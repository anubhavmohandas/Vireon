# ⚡ Vireon — Autonomous Multi-Agent Security Investigation Platform

> **Band of Agents Hackathon · June 2026**
> Point it at a repo. Walk away. Come back to a triage report, working patch, and GitHub PR — generated by 8 agents that argue with each other.

---

## What it does

Vireon runs an end-to-end security investigation autonomously:

1. Reads your repo's dependency stack
2. Fetches real CVEs from OSV.dev and NVD
3. Runs Semgrep static analysis
4. Uses an LLM to confirm which findings are actually exploitable
5. A second LLM agent argues back — trying to *disprove* the findings
6. Generates code patches and dependency bumps
7. A compliance agent reviews the patch (retries up to 3x if rejected)
8. Re-runs Semgrep to verify the fix works
9. Opens a GitHub PR — or saves a full draft if you have no token

No human in the loop. Every decision is logged with timestamp, agent name, confidence score, and reasoning.

---

## The 8 Agents

| # | Agent | Role | Key output |
|---|-------|------|-----------|
| 1 | **ThreatIntel** | Fetches CVEs, builds knowledge graph | `state.cves`, `state.graph` |
| 2 | **Static** | Semgrep scan (python, js, xss, secrets, owasp) | `state.findings` |
| 3 | **Exploitability** | LLM triage — real risk or false positive? | `state.confirmed` |
| 4 | **Challenger** | Red team review — actively tries to disprove | confidence adjustment |
| 5 | **Remediation** | Generates code patch + dep bumps | `state.patch_result` |
| 6 | **Compliance** | Security policy gate — approve or retry | `state.compliance_approved` |
| 7 | **Verification** | Applies patch, runs tests, re-runs Semgrep | `state.verify_results` |
| 8 | **PR** | Opens GitHub PR or saves draft | `output/pr_draft.md` |

The Challenger is why this is interesting. It's not a straight pipeline — agents 3 and 4 debate. If the Challenger can't find mitigating factors, that *strengthens* the case. Fused confidence below 0.3 aborts — no false-alarm PRs.

```
repo_path
    │
    ▼
┌─────────────────────────────────────┐
│  coordinator/coordinator.py         │  ← orchestrates phases, owns retry loop
└─────────────────────────────────────┘
    │
    ▼
┌───────────┐   ┌───────────────┐
│  Threat   │──▶│    Static     │   Phase 1: evidence gathering
│  Intel    │   │  (Semgrep)    │
└───────────┘   └───────────────┘
    │ cves, graph       │ findings
    └──────────┬────────┘
               ▼
        ┌──────────────┐
        │Exploitability│   Phase 2: LLM triage
        └──────────────┘
               │ confirmed[]
               ▼
        ┌──────────────┐
        │  Challenger  │   Phase 3: red team debate
        └──────────────┘
               │ confidence fusion
               ▼ (abort if < 0.3)
    ┌──────────────────────┐
    │  Remediation ⇄       │   Phase 4: patch loop (up to 3x)
    │  Compliance          │
    └──────────────────────┘
               │ approved patch
               ▼
    ┌───────────┐   ┌────────┐
    │Verification│──▶│  PR   │   Phase 5: verify + ship
    └───────────┘   └────────┘

            All agents share:
         memory/shared_state.py
    (asyncio.Lock, append-only timeline)
```

**`scanner/`** — 9 standalone modules (zero external dependencies beyond pip):

| Module | Replaces | Does |
|--------|----------|------|
| `stack.py` | — | Detects packages from requirements.txt, package.json, pyproject.toml, Pipfile |
| `osv.py` | — | OSV.dev batch API (no key needed) |
| `nvd.py` | — | NVD keyword search (NVD_API_KEY optional but improves coverage) |
| `graph.py` | — | networkx dependency graph + reachability |
| `semgrep.py` | — | Semgrep wrapper with venv binary resolution, excludes, timeouts |
| `llm_analyzer.py` | — | LLM exploitability analysis (groups by file, reads source) |
| `patcher.py` | — | LLM patch generator (delimiter-based format, avoids JSON escaping bugs) |
| `verifier.py` | — | Test runner + post-patch Semgrep re-scan |
| `github_pr.py` | — | GitHub PR via PyGitHub, fallback to markdown draft |

## Quickstart

```bash
git clone https://github.com/anubhavmohandas/vireon
cd vireon

python -m venv myvenv
source myvenv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# Edit .env — add FEATHERLESS_API_KEY (free) and NVD_API_KEY (free)

# Scan any repo
python main.py /path/to/your/repo

# Or run the demo (pre-seeded CVEs, no API keys needed for phases 1-2)
python demo_run.py
```

## Configuration

`.env` keys — all optional except one LLM key:

```bash
# LLM — pick one (priority: Featherless > AIML > Anthropic)

# CVE sources

# Band SDK (optional — runs in local mode without these)
BAND_REST_URL=https://app.band.ai/
BAND_WS_URL=wss://app.band.ai/api/v1/socket/websocket
THREAT_AGENT_ID=       # create at app.band.ai → Agents → New Agent
THREAT_AGENT_KEY=
# ... (one ID+KEY pair per agent — see .env.example)
```

LLM model used: **Qwen/Qwen2.5-72B-Instruct** via Featherless (ungated, OpenAI-compatible API).

## Band SDK Integration

Each agent extends `BandAgent` from the `thenvoi` SDK. When Band credentials are configured, agents connect via WebSocket and post live updates to a shared war room — you can watch the Challenger argue with Exploitability in real time.

Without credentials: local mode, full pipeline still runs, output goes to console + `output/`.

```python
class ChallengerAgent(BandAgent):
    name = "challenger"
    depends_on = ["exploitability"]

    async def execute(self) -> AgentResult:
        # ... red team review ...
        return AgentResult(verdict="confirmed", confidence=0.72, ...)
```

The coordinator posts confidence snapshots after every agent so the Band room UI can show the score rising and falling across phases.

## Why the Challenger matters

Most security pipelines are straight pipelines: scan → triage → patch. Vireon adds a deliberate adversarial step.

The Challenger has a negative weight in confidence fusion (`-0.15`). If it finds sanitization, auth gates, ORM protections, or unreachable code paths — confidence drops. If it *can't* find any of those — the case against the finding gets stronger. It's not a veto, it's a pressure test.

This mirrors how real security teams work: one engineer files a finding, another reviews it for false positives, a third writes the fix, a fourth checks the fix doesn't introduce new issues.
